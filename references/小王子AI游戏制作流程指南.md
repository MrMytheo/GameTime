# 小王子 AI 游戏制作流程指南

从故事与视觉参考到可运行的 3D 探索游戏

整理日期  2026 年 10 月 21 日

这份指南帮助个人开发者理解并执行一条 AI 辅助游戏制作流程。先完成一个能移动、能交互、能结束的小场景，再扩展星球和剧情，可以更早发现模型、动画和引擎之间的问题。

### 案例中的工具分工

Sac（@Saccc_c）的公开案例为《小王子：星辰之旅》。教程转载描述的分工是：Fable 5.1 整理需求，Image 2.5 制作视觉参考，Tripo 生成资产，Opus 5.5 配合 Blender 与 Unity 制作游戏，Astra 迭代调试。作者还使用 Auto-Rig Pro 和 Mixamo 处理角色动画。[1]

以上名称保留案例语境。实际复现时，应按所需能力选择当前可用的工具；具体版本、插件安装方式和费用以各产品文档为准。下文的任务拆分、提示词和验收清单为整理者补充的执行建议。

| 阶段 | 交付物 | 通过后再进入下一步 |
| --- | --- | --- |
| 需求 | 一页玩法说明 | 玩家目标与完成条件明确 |
| 视觉 | 场景设定与角色设定 | 造型和空间关系一致 |
| 资产 | 模型 贴图 骨骼 动作 | 导入引擎后可用 |
| 整合 | 可玩的场景 | 任务能从开始走到结束 |
| 发布 | 构建包与操作说明 | 目标设备实际运行通过 |

## 01 准备工具并确定第一个场景

### 先写一页玩法说明

建议用一个小星球作为练习范围：玩家从小屋附近出发，找到水壶，给玫瑰浇水，触发一段对话，再走到离开星球的位置。此处为演示设计，不代表原作游戏的完整玩法。

- 目标：明确玩家要做什么，以及什么状态代表成功。

- 操作：先确定移动、镜头和交互键；记录键鼠或手柄的支持范围。

- 内容：列出一名主角、一个场景、必要道具、对话和一个结束节点。

- 表现：记录色板、角色比例、光照方向和目标设备，供后续统一检查。

### 按能力准备工具

| 能力 | 用途 | 准备完成的判断 |
| --- | --- | --- |
| 文本与编码 AI | 需求拆解 脚本 排错 | 能读取项目并修改测试脚本 |
| 图像 AI | 场景与人物参考 | 能输出同一设计的不同视角 |
| Tripo | 图像或多视图生成模型 | 导出一个测试模型并能导入 |
| Blender | 修模 材质 骨骼 动画 | 能打开模型并保存工程 |
| Unity | 交互 场景 UI 构建 | 空项目可运行且可构建 |

### 先验证工具之间的传递

用一个简单道具走完“生成 → 导出 → Blender → Unity”的路径，检查大小、朝向、贴图和材质。随后用一个临时角色验证站立和行走。确认传递可用后，再批量制作正式资产。

如果让 AI 通过脚本或 MCP 操作编辑器，先测试创建一个物体、保存场景和读取错误日志。连接器名称和配置方法应按所用插件说明确认。

### 保存工程和版本

建议分别保存需求、参考图、原始生成资产、Blender 源文件、Unity 工程、构建包与检查截图。资产名称使用固定编号，例如 CH_Prince_001、PR_WateringCan_001。每次通过验收后保存一个可回退版本，并记录工具版本、生成参数和资产来源。

## 02 制作场景与环境资产

### 把画面变成可搭建的空间

先选定主视觉，再绘制或生成布局参考。为小屋、道路、玫瑰和出口确定位置，用主角身高作比例尺。对无法从图中判断的背面、门洞和坡面，在布局图中明确标注。

- 氛围图说明色彩、光照和情绪；布局图说明距离、通道宽度与遮挡。

- 室内与室外要有一致的门窗位置、墙厚和可通行尺寸。

- 先在 Unity 中用方块和地面搭白盒，实际走一遍，再投入细节资产。

### 按用途拆分资产

| 类别 | 建议制作方式 | 重点检查 |
| --- | --- | --- |
| 玫瑰 水壶 岩石 | 单件生成后导入 | 轮廓 贴图 比例 |
| 地面 道路 墙体 | 编辑器或脚本搭建 | 连接处 坡度 碰撞 |
| 小屋 门 家具 | 按交互需求拆部件 | 门洞 支点 可进入空间 |
| 草 花 云 背景 | 优先重复使用与简化 | 遮挡 数量 运行开销 |

### 逐件生成与导入

每件资产写清外形、材质、尺寸关系和可动部件。导出后在 Blender 中检查孔洞、法线、UV 和多余几何，再到 Unity 中核对贴图及材质。先保留原始模型，再制作游戏使用的简化版本。Tripo 的格式转换提供 FBX、GLTF 等选项；格式能保存的内容不同，应按模型是否含骨骼和动画选择。[3]

### 组合环境并保留游玩空间

先摆放地面和主要建筑，接着确定路线与交互点，最后补植被、灯光和装饰。为路面和建筑设置必要碰撞，让镜头能看清主角和交互物。建议保存入口、任务点和出口三个固定截图机位，方便比较每次修改。

### 本阶段验收

玩家能走完整条路线；关键道具容易识别；门洞和坡面可通过；从主要机位看不到明显悬空或穿插；场景文件重新打开后模型与材质仍然正确。

## 03 制作角色并验证动画

### 先固定角色设计

给角色准备正面、背面与侧面参考，明确头身比例、衣服层次、手指和鞋的形状。各视图保持同样的发型和服装细节。使用便于识别关节的姿态，避免围巾、衣袖和道具遮住手臂。

### 检查模型再绑骨

模型生成后，先查看手、脸、腋下和腿之间的结构。发现肢体粘连或手指异常时，先修几何。自动绑骨完成后，测试肩、肘、髋、膝和手指的转动，检查皮肤权重。Tripo 官方说明也将肩部、髋部与手指列为重点检查区域。[4]

案例使用 Auto-Rig Pro；也可以评估 Tripo 或 Mixamo 的绑骨能力。先选定主骨架，再配置动作的适配方式。Mixamo 支持上传自定义角色进行绑骨，也支持上传 FBX 格式的已有骨骼角色。[5]

### 建立最少动作集合

| 动作 | 用途 | 验收方式 |
| --- | --- | --- |
| 站立 | 默认与等待状态 | 循环接缝不突跳 |
| 行走 | 探索和接近道具 | 速度与脚步尽量匹配 |
| 转身 | 调整朝向 | 身体不突然扭曲 |
| 拿取或浇水 | 完成核心交互 | 手和道具接触稳定 |

### 统一骨架与位移规则

动作能在预览中播放后，再导入 Unity。人形角色可按官方导入流程设置 Humanoid、生成 Avatar，并检查骨骼映射；同一骨架的动画可以复用对应 Avatar。[6] 确定移动由控制脚本驱动，还是由动作根位移驱动，避免同一次位移被执行两遍。

### 处理拿道具的接触

把拿起、持握、放下分别检查。定义道具的握持点、附着时刻和释放时刻；在需要时使用手臂 IK 调整姿态。逐帧确认手掌贴合把手，道具不会瞬移，动作结束后能正确回到站立。保存一个含测试动作的角色工程，供后续回归检查。

## 04 在 Unity 中连接交互与剧情

### 先让任务完整运行一次

使用白盒场景和临时角色，先接通移动、镜头、交互提示、对话与任务结束。每个功能都能实际操作后，再逐步替换正式模型和动作。

1. 角色移动与镜头：确定速度、转向和碰撞方式，让玩家可以稳定走到任务点。

2. 交互检测：靠近水壶显示提示；离开范围后提示消失；超出范围不能拿取。

3. 任务状态：把“未拿水壶、已持有、浇水完成、允许离开”设为明确状态。

4. 动作与反馈：浇水动作到达约定时刻后触发水流和玫瑰反馈，完成后更新任务状态。

5. 对话与离开：对话可关闭或跳过；只有满足条件时才能触发结束。

### 明确数据由谁维护

建议由任务逻辑统一保存任务状态，UI 读取状态显示提示，动画事件只报告动作时刻。这样可以减少“画面已浇水，但任务还没完成”之类的不同步问题。为每个任务状态定义进入条件和退出条件。

### 交给编码 AI 的任务要足够具体

一次实现一个可验证功能。例如：“玩家进入交互范围时出现 E 键提示，按键后拿起水壶；持有期间不能重复拿取；离开范围时隐藏提示。”同时提供引擎版本、现有脚本、场景物体名称和预期结果。

让 AI 在交付时说明改动了哪些文件、需要在 Inspector 中连接哪些引用、如何运行和验证。编译通过后，还需要在运行模式实际执行完整任务。

### 本阶段检查清单

- 从新开游戏到结束，任务可以连续完成。

- 重复按键、快速进出范围、取消对话不会卡住任务。

- 道具持有状态、任务提示、动画和场景表现一致。

- 失败或中断后可以重来；正式角色替换后交互仍然可用。

- 如果提供存档，退出重进后恢复到明确且可继续的状态。

## 05 通过反馈迭代并发布

### 每轮只解决可以描述清楚的问题

保存固定机位截图与完整游玩录像，把问题写成“观察到的现象、预期结果、出现位置、复现步骤”。例如：“浇水到第 2 秒时右手离开把手；预期全程握持；从左侧机位可见。”修复后复查同一路径和相邻动作。

| 问题 | 优先排查 | 复查方法 |
| --- | --- | --- |
| 贴图丢失或发灰 | 导出贴图 材质映射 | 重开工程并检查材质 |
| 角色扭曲 | 骨骼映射 权重 姿态 | 逐关节与逐动作预览 |
| 脚滑或位置跳动 | 速度 根位移 动作切换 | 录制走停转全过程 |
| 道具悬空 | 握持点 附着时序 IK | 侧面逐帧看接触 |
| 运行卡顿 | 几何 贴图 阴影 渲染开销 | 目标设备实际测量 |

### 在目标设备测量

记录设备、分辨率、画质、加载时间和帧率。根据测量结果再减少重复资产的开销、调整贴图和阴影，或分阶段加载。保留同一条测试路线，比较修改前后的表现。不要用高性能开发机的单次结果替代目标设备验证。

### 构建和浏览器检查

若目标是网页，使用所选 Unity 版本支持的 Web 构建流程，按部署要求提供完整构建文件与服务器配置。Unity 官方说明 Web 构建会生成运行所需的 Build 文件夹。[7] 上线前从实际网址测试加载、输入、音频、任务完成与刷新后的行为。

案例游戏首页提示需要电脑，建议 Chrome 或 Edge，手机和平板暂不支持。[2] 复现项目应单独声明自己已经测试过的设备与浏览器。

### 阶段交付

- 第一关：一个可操作的白盒场景。

- 第二关：一名正式角色和必要道具，完成一次核心交互。

- 第三关：视觉与声音完善，关键问题修复，目标设备运行通过。

- 第四关：发布包、操作说明、已知问题与可回退工程归档。

## 06 可复制的工作提示词

以下模板为整理者编写。将方括号替换为自己的内容，并提供相关参考图、工程文件或日志。先完成当前阶段验收，再发起下一项任务。

### 模板一 确定最小玩法

```text
我要做一个以[故事主题]为背景的 3D 探索游戏，首版只做[场景]。请列出玩家目标、操作、任务状态、必要角色与道具，以及从开始到结束的操作路径。对缺少的信息逐项提问。输出一页需求说明和可验证的完成条件。
```

### 模板二 形成场景制作清单

```text
参考附图和已确认的玩法，列出场景中的每项资产、尺寸关系、交互需求、制作方式和导入后的检查项。指出哪些结构需要拆开以支持进出、拿取或移动。对图片中无法确定的空间关系先列为待确认项。
```

### 模板三 检查角色与动作

```text
请检查[角色文件]的骨骼、关节权重和[动作文件]的适配情况。先运行站立、行走、抬手、弯腿测试，记录具体异常和出现的帧。修复后提供同机位的前后对比，并保留修复前工程。
```

### 模板四 实现单个交互

```text
在现有 Unity 项目实现[交互]。触发条件是[条件]，成功反馈是[反馈]，退出或重复操作规则是[规则]。先检查现有脚本和对象引用，再实现并运行验证。交付改动文件、编辑器连接步骤、验证结果及剩余问题。
```

### 模板五 根据证据修复

```text
问题现象：[现象]。复现步骤：[步骤]。期望结果：[结果]。相关截图、视频或日志：[附件]。请先定位原因，再做最小修改；修复后重走同一路径，并检查受影响的邻接功能，说明证据和结论。
```

### 从第一个场景开始

先写好一页玩法说明，再把一个简单模型导入 Unity 并做出可走动的场景。最先需要证明的是：资产能传递、角色能控制、任务能完成。通过这三项后，再增加美术细节、第二个星球和更长的剧情。
